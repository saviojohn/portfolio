## Execution Process

> **Important:** Do not skip phases. Show all reasoning and decision-making at each stage.

### Phase 1 — Research: Modern Portfolios
Research the current state of developer and creative portfolios. Note what is common, what is expected, and what the baseline looks like.

### Phase 2 — Research: Award-Winning Digital Experiences
Study Awwwards, FWA, CSS Design Awards, and similar platforms. Identify what elevates experiences to award-winning status.

### Phase 3 — Research: Portfolio Clichés to Avoid
Catalogue every recurring pattern, visual, or interaction model that has become overused. This becomes the explicit exclusion list.

### Phase 4 — Generate 15 Radically Different Concepts
Create 15 distinctly original portfolio concepts. Each must differ in storytelling model, interaction paradigm, and visual identity — not just surface aesthetics.

### Phase 5 — Score Every Concept
Score each concept against these criteria (0–100 per criterion):

| Criterion | Weight |
|-----------|--------|
| Originality | High |
| User Experience | High |
| Technical Feasibility | Medium |
| Recruiter Appeal | High |
| Accessibility | Medium |
| Performance | High |
| Scalability | Medium |
| Maintainability | Medium |

### Phase 6 — Eliminate Weak Concepts
Remove any concept scoring below threshold on originality, UX, or performance feasibility.

### Phase 7 — Select the Strongest Concept
Choose the highest-scoring surviving concept. Justify the selection with explicit reasoning.

### Phase 8 — Stress-Test the Concept
Challenge the selected concept against:
- Technical risk
- Performance risk
- Accessibility gaps
- Maintainability concerns
- Mobile experience quality
- Recruiter comprehension speed

### Phase 9 — Refine to 95+ Originality
Iterate on the concept until the originality score exceeds 95/100. If it cannot reach 95+, return to Phase 4.

> **Only after Phase 9 is complete should any design or code work begin.**

## Design System

Generate a premium design system that rivals Apple, Stripe, Linear, Vercel, and Raycast in quality and coherence.

### Required Systems

**Color System**
- Primary, secondary, accent, and neutral palettes
- Dark mode default; light mode supported
- Semantic color tokens (background, surface, text, border, interactive states)
- All values accessible at WCAG AA contrast minimum

**Typography System**
- Display typeface (editorial/serif — one Google Font)
- UI typeface (geometric sans — one Google Font)
- Full responsive type scale (fluid, clamp-based)
- Line height, letter spacing, and weight tokens

**Motion System**
- Easing curve library (no linear transitions anywhere)
- Duration tokens (instant, fast, medium, slow, cinematic)
- `prefers-reduced-motion` override for every animation
- Animation personality defined: describe the motion "character"

**Spacing System**
- Base-4 or base-8 spacing scale
- Responsive spacing tokens
- Component-level and layout-level spacing documented

**Component System**
- Atomic components: Button, Badge, Tag, Input, Modal, Card, Icon
- Compound components: Navigation, Project showcase, Timeline, Contact form
- Each component: props documented, states defined, accessibility attributes included

**Iconography System**
- Icon style defined (outline, filled, duotone, custom)
- Consistent stroke weight and optical sizing
- All icons accessible (aria-label or aria-hidden as appropriate)

### Design Reference Analysis
Before creating the design system, analyse and document what makes these products feel premium:
- Apple, Stripe, Linear, Vercel, Notion, Framer, Figma

Extract principles. Do not copy. Apply those principles to create an **original** design language.

The mobile experience must be **equally emotionally impressive** as desktop. Do not reduce features — redesign them for touch. If a desktop effect is too GPU-expensive for mobile, create a mobile-specific alternative that delivers the same emotional impact.

Mobile is a first-class experience, not a degraded one.

## Accessibility

### Standard
- **Minimum:** WCAG 2.1 AA
- **Target:** WCAG 2.1 AAA where achievable

### Required Implementation
- Full keyboard navigation (all interactions accessible via keyboard)
- `prefers-reduced-motion` support on every animation (disable or reduce when set)
- Visible, styled focus states on all interactive elements
- Semantic HTML5 landmarks (`<main>`, `<nav>`, `<header>`, `<footer>`, `<section>`, `<article>`)
- Screen reader compatibility (tested with NVDA/VoiceOver)
- WCAG AA colour contrast on all text and interactive elements
- One `<h1>` per page; logical heading hierarchy
- All images: meaningful `alt` text or `aria-hidden="true"` for decorative images
- All form inputs: associated labels
- All icons: `aria-label` or accompanied by visible text

> **Accessibility must be integrated from the start — not added later.**

## Security Architecture

### Threat Model — Protect Against
- XSS (Cross-Site Scripting)
- CSRF (Cross-Site Request Forgery)
- SSRF (Server-Side Request Forgery)
- Injection attacks (HTML, SQL if applicable, command)
- Content poisoning
- Prompt injection (if AI features are present)
- Supply chain attacks via npm
- Data leakage (secrets in client bundle, verbose error messages)

### Required Security Headers
```
Content-Security-Policy: script-src 'self'; no unsafe-inline
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

### Secrets Management Rules
- Zero secrets or API keys in client-side code
- All sensitive values in `.env.local` (gitignored)
- Only server components and API routes access `process.env.*` secrets

### Contact Form Security
- Input sanitisation (strip HTML, trim, validate format)
- Rate limiting: max 5 submissions per IP per hour
- Server-side validation (never trust client-side only)

### Required Security Deliverables
- Threat model document
- Security checklist
- Secure deployment strategy

## Dependency Audit

For every proposed package, document:

| Field | Required |
|-------|---------|
| Purpose | What it does and why it is needed |
| Bundle impact | Compressed size added to bundle |
| Maintenance status | Last release, open issues, commit frequency |
| Weekly downloads | Popularity signal |
| Security history | Known CVEs, past incidents |
| Alternatives considered | What was evaluated and rejected, and why |

### Categorised Output Required

**Approved Package List** — packages that passed all criteria

**Rejected Package List** — packages considered but excluded, with reason

**Watch List** — packages approved but requiring monitoring (e.g. recent maintainer change, one-person project)

**Dependency Risk Score** — overall score for the dependency footprint

### Selection Principles
- Prefer native browser APIs over packages where feasible
- Prefer lightweight, focused libraries over large frameworks for small tasks
- Prefer actively maintained libraries (commits within 6 months)
- Reject abandoned packages
- Reject packages with duplicate functionality already covered
- Reject packages with unresolved high/critical CVEs

## npm Supply Chain Audit

### Required Configuration
Add to `.npmrc`:
```
minimumReleaseAge=1440
```
This prevents installation of packages published less than 24 hours ago — blocking most supply chain worm attacks.

### Audit Criteria Per Package
- Release frequency and version history
- Contributor quality and bus factor
- Security history and CVE record
- Vulnerability disclosure and response time
- Ecosystem reputation and community trust

### Required Recommendations
- Safe pinned version for each package (exact versions, no `^` or `~` on critical packages)
- Lockfile strategy (`package-lock.json` committed; use `npm ci` in CI)
- Update strategy (scheduled review cadence)
- Vulnerability monitoring strategy (Dependabot or equivalent)
